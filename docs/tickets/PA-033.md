# PA-033: Decide delivery ownership and numeric retry policy

Stage: [S3 - Background execution and recovery](../roadmap.md#s3-background-execution-and-recovery)
Status: Not started
Depends on: [PA-006](PA-006.md)

## Expected result

Specify the queue/result mechanism and bounded lifecycle policy before implementing dispatch and recovery.

## Scope

- Select queue/result transport and define authenticated delivery, execution claim ownership, atomic report acceptance, dispatch reconciliation, and expired-attempt fencing.
- Record numeric queue wait, attempt lease/renewal, execution deadline, delivery timeout, maximum attempts, retry delay/backoff cap, and reconciliation interval with units.
- Classify retryable versus deterministic errors and write an event table for duplicate jobs/results, missing starts, publish/commit failure, worker loss, and late attempts.

## Acceptance criteria

- [ ] Each event has one authoritative state/attempt outcome aligned with the contracts and a named responsible component.
- [ ] All required timers/attempt limits have finite initial values with rationale; relationships between lease renewal, execution timeout, retries, and delivery are explicit.
- [ ] The design identifies how durable scan creation and job publishing recover across the chosen database/queue boundary without assuming exactly-once delivery.

## Verification

- Walk failure scenarios and timing examples to check that stale attempts cannot win and accepted work cannot remain indefinite.
- Validate selected transport capabilities against primary documentation when executing this ticket and record the configuration mapping.

## Out of scope

Queue integration code, performance guarantees, public request quotas, and an unbounded generic retry framework.
